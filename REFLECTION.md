# Written Reflection — GradeTracker Project

## Technical Challenge: Connecting the Frontend to a PHP Backend with Sessions

One of the most significant technical challenges I encountered during this project was integrating the JavaScript frontend with the PHP backend while maintaining session-based authentication. Initially, my approach was to use standard HTML form submissions with `action` attributes pointing directly to PHP files. While this worked for basic functionality, it caused full page reloads on every action, which broke the single-page experience I was aiming for and made it impossible to update the grade table dynamically without refreshing.

The core problem became clear when I switched to using the Fetch API for asynchronous communication. Although the PHP endpoints were working correctly when accessed directly in the browser, the Fetch requests from `index.html` were returning `Unauthorized` errors. After investigating, I discovered that the issue was a mismatch between how PHP sessions work and how static HTML files are served. Because `index.html` is a static file and not a PHP page, it cannot check or maintain session state on its own. When the user logged in through `login.php`, the session was created correctly, but subsequent Fetch calls to endpoints like `addGrade.php` were correctly checking `$_SESSION["user_id"]` — the session cookie was being sent by the browser automatically, which meant the fix was simply ensuring the user always accessed the application after logging in through the PHP login page rather than opening `index.html` directly.

This experience taught me the importance of understanding how the browser handles cookies and sessions across different types of requests. It also reinforced why proper authentication flow matters in web applications — not just for security, but for the overall user experience. Going forward, I would consider building a PHP entry point that checks session state before serving the main page, to prevent unauthenticated access entirely.
